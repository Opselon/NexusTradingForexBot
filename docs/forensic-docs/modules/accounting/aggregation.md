# src/nexus_scalp/accounting/aggregation.py

- PURPOSE: Pure period & drawdown aggregation math — turns canonical `TradeRecord` / `AccountSnapshot` sequences into `PeriodReport` and `DrawdownReport`. Free of I/O so the same code path serves the live API, the background worker and any rebuild: one methodology, no consumer-specific variants.
- ARCHITECTURE LAYER: Application (pure computation layer under AccountingCore; also imported directly by reporting/engine.py for excursion normalization).
- RESPONSIBILITY: Statistical honesty rules (ratios undefined for the sample stay None, never clamped to 1.0/0.0; R-based stats only over trades with a reconstructed risk basis, `r_sample_count` exposes the thinness), MAE/MFE sign normalization, period aggregation, THE canonical drawdown method, and the advanced risk/return metric set.
- DEPENDENCIES:
  - `accounting.models` → AccountSnapshot, DrawdownReport, PeriodReport, TradeOutcome, TradeRecord.
  - `accounting.periods.PeriodBounds` → half-open interval + `contains()`.
  - `math`/`statistics` (imported lazily inside `compute_advanced_metrics`).
- CONNECTS TO: `AccountingCore.period_report/_compute_period/drawdown_report` (core.py:450-454, 487-493), `reporting/engine.py:_stage_excursion` (imports `_mae_value`/`_mfe_value` directly, engine.py:530), and re-exported through `accounting/__init__.py`. This module IS the drawdown methodology (`compute_drawdown`).
- KEY CONCEPTS:
  - Sign convention (TASK-1 forensic audit 2026-08-18, lines 34-41): MAE is adverse and MUST be negative money, MFE favourable and MUST be non-negative; raw ledger columns historically stored mixed conventions. `_mae_value` (line 42): stored negative MAE_usd wins; otherwise derive `-abs(points) * usd_per_point`; missing → 0.0. `_mfe_value` (line 56): a stored NEGATIVE MFE_usd is a sign-convention violation and is treated as zero (never a negative "anti-excursion"). `_usd_per_point` (line 69): derives USD/point from the MAE pair, falling back to the MFE pair.
  - `aggregate_period(bounds, trades, snapshots)` (line 80): buckets by `closed_at` inside the half-open bounds (trades with None `closed_at` are excluded). `has_data` false when neither trades nor snapshots existed → explicit empty state, not a zeroed row. Win/loss counts come from `trade.outcome` (decided by money); `gross_profit` sums net PnL of wins, `gross_loss` sums |net PnL| of losses. Best/worst trade from all net PnLs.
  - Win-rate reconciliation contract (lines 156-191): `win_rate` = wins/decided (classic, scratches excluded); `win_rate_all` = wins/total_trades; `loss_rate_decided` = losses/decided; `loss_rate_all`; `pnl_weighted_win_rate` = gross_profit/(gross_profit+gross_loss); `win_rate_denominator` label "DECIDED"/"ALL_TRADES"/"NONE". Phase-16 additions: `expectancy_breakeven_incl` (net/all), `avg_pnl_per_decided` (net/decided), `total_costs` = commission+swap, `cost_drag_pct` (% of gross_profit+costs), `stop_loss_share` (share of losses ended at a protective stop), `avg_loss_r` (mean realized_r over losers only).
  - Profit factor stays None with zero losses (line 225) — "inf" or 1.0 would both mislead. `average_r`/`r_sample_count` only over trades with `realized_r` (lines 228-230). `total_risk_deployed` only when at least one trade had a risk basis (line 234-235).
  - Envelope from snapshots (lines 237-249): starting/ending balance & equity from first/last ascending snapshot; `pnl_pct` = net_pnl/starting_balance; intra-period drawdown via `intraperiod_drawdown` (line 254) which needs >= 2 samples to express a drawdown (single snapshot → (None, None)).
  - `compute_drawdown(snapshots)` (line 280): THE canonical drawdown methodology. Peak-to-trough on the equity series, percent of running peak. Tracks max drawdown %/USD/at; `current_dd_start` records where the current uninterrupted drawdown began (peak_at of the peak that started it); `last_recovery` records the most recent completed peak→recovery cycle (lines 308-327). `in_drawdown = current_usd > 0.0`; `recovery_pct` = how much of the max drawdown has already been recovered (100.0 when fully recovered, line 350-351); `recovery_duration_sec` from the last completed cycle.
  - `compute_advanced_metrics(trades, equity_points)` (line 361): the big sample-honest dictionary — PF, expectancy, win/loss rates (same reconciliation contract as PeriodReport, lines 500-520), streaks, R coverage (`r_coverage_ratio = r_sample/total`, line 556), MAE/MFE R factors, `win_mae_capture_pct` / `loss_efficiency_pct` (lines 564-575), profit/loss skew (raw third moment, lines 578-585), Sharpe/Sortino on equity returns (per-interval ratios, square-root-of-n scaled, lines 588-613), `annualized_volatility_pct` via a ~1-week-per-year-slice proxy (lines 614-617 — honest about being a proxy), Calmar/recovery factor (lines 620-633), SQN (needs >= 5 R samples, lines 636-642), profit_standard_error t-stat proxy (lines 645-651).
- HOT PATH / PERFORMANCE: All single-pass loops over in-memory lists; `compute_advanced_metrics` imports math/statistics lazily. Called from worker cycles and API requests — bounded by MAX_TRADE_ROWS/MAX_SNAPSHOT_ROWS upstream.
- EDGE CASES & PITFALLS:
  - `_stage_excursion` in reporting/engine.py re-computes `_mae_value`/`_mfe_value` from `TradeRecord` — the excursion normalization is NOT baked into TradeRecord at normalize time, so the excursion sign convention lives in TWO places (this module + callers importing these private helpers). The private (`_`-prefixed) name is the only thing preventing wider drift.
  - `intraperiod_drawdown` starts `peak` from `snapshots[0].equity` — it assumes the caller's snapshot slice is the full window (it is, via core.load_snapshots).
  - `compute_drawdown` treats `peak_balance` as a running max of balance (line 328) but drawdown itself is equity-based — balance and equity can diverge with floating PnL.
  - `avg_loss_r` (line 210-216) uses `realized_r` of losers; a loser without a reconstructed risk basis silently drops out — the count of losers backing `avg_loss_r` is not exposed.
  - Cost drag uses `gross_profit + total_costs` as denominator (line 196) — chosen so negative-return samples stay meaningful, but note it is NOT gross_profit alone.
