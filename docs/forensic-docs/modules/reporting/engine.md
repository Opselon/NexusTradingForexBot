# src/nexus_scalp/reporting/engine.py

- PURPOSE: `PerformanceReportEngine` — deterministic multi-stage daily/weekly performance intelligence generator. READ-ONLY enrichment over `AccountingCore`: never writes financial truth, never opens/closes trades, never modifies risk/model/news settings.
- ARCHITECTURE LAYER: Application (report generation layer above the canonical accounting facade).
- RESPONSIBILITY: Orchestrate ~24 deterministic stages (SNAPSHOT → OUTCOMES → PROFIT_DECOMPOSITION → DISTRIBUTION → R_MULTIPLE → EXCURSION → HOLDING/EXIT → STREAK → RISK → DRAWDOWN → STRATEGY → REGIME → SESSION → MODEL → EXECUTION → NEWS → BEHAVIORAL → LOSS/PROFIT DRIVERS → PERIOD_COMPARE → ANOMALY → HEALTH → INSIGHTS) and assemble them into one `ReportContainer`. The canonical `PeriodReport` from `AccountingCore.period_report` is the single source of money truth; the report's performance section mirrors it exactly.
- DEPENDENCIES:
  - `accounting.core.AccountingCore` → period report, load_trades, live_state, drawdown_report, _connect/_enabled (private SQLite access).
  - `accounting.models` → PeriodReport, TradeOutcome, TradeRecord.
  - `accounting.periods` → PeriodKind, ensure_utc, period_bounds, utc_now (+ local `timedelta` import inside generate).
  - `accounting.aggregation` → `_mae_value`, `_mfe_value` (private module helpers, imported lazily inside `_stage_excursion`).
  - `reporting.insights` → classify_session, classify_trend, compare_periods, compute_anomalies, compute_health_score, evidence_level, generate_insights, make_report_id, make_snapshot_id.
  - `reporting.models` → all section dataclasses.
  - `intelligence.models.BehaviorAnalysisStatus` → behavioral/anomaly state labels (imported lazily in the two stage methods).
  - `observability.logging.get_logger` → `[TELEGRAM_REPORT]` event logging.
- CONNECTS TO: Telegram notifier (via `format_telegram_daily`/`format_deep_report` on the produced container), `/api/account/performance/intelligence` REST endpoint, and tests. Instantiated with an AccountingCore and a PeriodKind (default DAY).
- KEY CONCEPTS:
  - `generate(at, previous_compare)` (line 119): deterministic for a fixed `at` and unchanged DB state. Pipelines: resolve bounds; make report/snapshot ids; load the canonical base report via `core.period_report(use_cache=True)` (line 143); load the SAME window's trades via `core.load_trades(since=bounds.start, until=bounds.end)` (line 145 — note: this bypasses the cache and re-pulls up to 20k rows even when the base came from cache); previous-period base for comparison (lines 150-159); run every stage; then run `compute_anomalies`, `compute_health_score` and `generate_insights` on progressively richer `_as_report` containers (lines 186-283); final `evidence = evidence_level(performance.trades)`; log COMPLETE with trades/pnl/duration.
  - `_EXIT_RAW_MAP` (line 71): exit-classification labels → report group labels; note `PROFIT_GIVEBACK_PROTECTION → TRAILING_STOP` and `EMERGENCY_CLOSE` (a raw value NOT produced by normalize's mechanism map) → `EMERGENCY_EXIT`. `_normalize_exit` (line 1247) falls back to the raw string when unmapped.
  - Blocker taxonomy (`_BLOCKED_MODEL/_POLICY/_RISK/_EXPOSURE/_EXECUTION`, lines 86-99): maps `blocked_by` values to the funnel's rejection classes; UNKNOWN blockers default to `policy_rejected` (line 864) — a deliberate "when in doubt, policy layer" choice for the funnel census.
  - `_stage_snapshot` (line 401): account envelope from live adapter, degraded to None when unavailable; `realized_pnl` from base report; `drawdown_pct` documented as the PERIOD drawdown (TASK-1 label fix) via `core.drawdown_report(lookback_days=1)` (line 420).
  - `_stage_performance` (line 436): mirrors the canonical PeriodReport EXACTLY (preserve-truth contract); payoff_ratio = avg_win/|avg_loss|; `median_trade/median_win/median_loss` hardcoded None (lines 463-465).
  - `_stage_distribution` (line 474): median win/loss from trade lists; skew via `_skew` (needs >= 2 values, line 1251).
  - `_stage_r` (line 501): R stats over `realized_r`-bearing trades only, `coverage_ratio = n_r / n_closed`.
  - `_stage_excursion` (line 523): uses the canonical `_mae_value`/`_mfe_value` normalization. MAE filter `v <= 0.0` KEEPS zeros ("a book of scratch trades reports avg MAE 0.0, not None" — matches the pre-existing test contract, lines 536-537); MFE filter keeps `v > 0.0` (zero-MFE trades excluded — a deliberate asymmetry vs MAE). `mfe_capture_ratio = Σ realized net PnL / Σ favourable excursion` (line 555) — a PORTFOLIO/population ratio that can be negative for a net-negative period, explicitly distinct from accounting/retention.py's per-trade capture (documented lines 543-550); `avg_giveback` = mean(MFE - realized) over MFE>0 trades.
  - `_stage_exits` (line 590): census by normalized exit, SORTED by count descending; win_rate over decided-only; avg_r over realized_r-bearing.
  - `_stage_streaks` (line 613): breakeven RESETS both streaks (line 624-625).
  - `_stage_risk` (line 637): risk utilization = total_risk_deployed/starting_balance; margin utilization from live adapter; `exposure_utilization_pct` is ASSIGNED the same value as margin_util ("same basis on MT5 when available", line 659); `max_concurrent_positions` from `getattr(live, "positions", [])` — note LiveAccountState has NO `positions` attribute and never populates it (core.live_state only sets open_positions count), so this is ALWAYS 0.
  - `_stage_drawdown` (line 673): TASK-1 fix — carries BOTH the 90-day historical max (`drawdown_window="90D"`) and `period_drawdown_pct` (1-day window), resolving the shared-label confusion documented in the comment (lines 674-681); `recovery_factor` hardcoded None (line 691).
  - `_stage_strategies` (line 700) / `_stage_regimes` (line 740) / `_stage_sessions` (line 773): attribution buckets with `evidence_level(len(group))`; sessions classify the UTC OPEN hour (trades without opened_at are skipped); strategy confidence/lifecycle_state are left None/"" (lines 733-734) — registry data (via `core.strategy_contributions`) is NOT used here.
  - `_stage_model` (line 802): reads `audit_signals` for the period window, probes the JSON payload for probability fields via `_probe` (buy/sell/no_trade/confidence, lines 838-841), and re-tabulates the funnel TWICE — once for executable actions (BUY/SELL MARKET/LIMIT with a blocked_by, lines 851-867) and once for NO_TRADE rows carrying a blocked_by reason (lines 879-897), the TASK-1 fix for the observed production stream recording every rejection as action=NO_TRADE. Executed = unblocked executable action rows. `prediction_to_execution_rate = executed / total_trade_signals` (dispatchable intents), `prediction_to_trade_rate = executed / len(rows)` (ALL predictions — the corrected label, lines 907-913). `prediction_to_win_rate` stays None (line 915-927).
  - `_stage_execution` (line 938): `audit_orders` latency/reason/action for the window; rejections via substring match on reason ("reject"/"fail"/"breakeven lock failed"); fill_ratio = "Executed order" acceptances / ("Executed order" + "Generated candidate") dispatch attempts — the TASK-1 corrected denominator (lines 966-983).
  - `_stage_news` (line 997): news provenance via `entry_reason` containing "NEWS"/"HIGH"/"IMPACT" — reads ledger text, no news tables.
  - `_stage_behavioral` (line 1020) / `_stage_anomaly_state` (line 1094): read `behavior_detections`, `behavior_analysis`, `anomaly_events` for the period's tickets (bounded to first 500 tickets — a >500-trade day silently analyzes only part). Both return truthful NO_DATA when no analysis ever ran; state CLEAR/FLAGS_FOUND/ANOMALIES_FOUND from evidence. Note NO_DATA is used instead of the INSISTENT INSUFFICIENT_EVIDENCE state at the section level, while the formatter checks both.
  - `_stage_loss_drivers` (line 1159) / `_stage_profit_drivers` (line 1191): bucket losses/wins by strategy_id (UNKNOWN_STRATEGY bucket for unattributed), sorted by |Σ pnl| / Σ pnl, take top 5.
  - `_stage_compare` (line 1221): `compare_periods(base.to_dict(), prev_base.to_dict(), ...)`; has_data=False when no previous period with data.
  - `_as_report` (line 333): the assembly helper (called 4× per generate — a long positional signature that is the single coordination point for the container).
- HOT PATH / PERFORMANCE: Report generation runs off the tick path (periodic/on-demand). Costs: up to 20k ledger rows re-pulled per generate (line 145) + one audit_signals + one audit_orders + 2 behavioral queries + 3 drawdown queries (90D, 1D in `_stage_snapshot`, 1D in `_stage_drawdown`). IN() placeholders are capped at 500 tickets in behavioral/anomaly stages but NOT in the identity join (core chunks at 400 — fine). No caching of the generated ReportContainer itself.
- EDGE CASES & PITFALLS:
  - `_stage_model` counts `executed_count` in the FIRST pass only for unblocked executable actions; NO_TRADE rows (even unblocked ones) never increment `trade_executed` — consistent with the production stream, but a hypothetical unblocked NO_TRADE is not "executed" by definition. Rows where BOTH passes could match (executable action AND NO_TRADE) cannot happen (actions are mutually exclusive) — the double-pass cannot double count (comment lines 875-878).
  - `_stage_behavioral`/`_stage_anomaly_state` silently truncate to 500 tickets — a >500-trade period yields partial census with no log.
  - Behavioral state NO_DATA vs formatter: `_behavioral_lines` in telegram_format treats NO_DATA as "no canonical behavior analysis exists"; but engine can also return ANALYSIS_FAILED which the formatter also lists — fine, but INSUFFICIENT_EVIDENCE is only produced by the formatter-side branch, never by the engine.
  - `_stage_news`: `inactive = [t for t in closed if t not in active]` (line 1002) is O(n²) list membership — fine at 20k, and correct because active ⊆ closed; NewsSection() empty when a period has no closed trades.
  - The private-helper import `from nexus_scalp.accounting.aggregation import _mae_value, _mfe_value` (line 530) couples the reporting layer to accounting internals; the normalization is deliberately NOT duplicated, but any rename in aggregation breaks engine silently at import time.
  - `_stage_risk.exposure_utilization_pct = margin_util` (line 659) makes the two fields structurally identical; if MT5 margin and exposure ever diverge (e.g. netting vs hedging accounts), this alias silently reports the wrong number for one of them.
