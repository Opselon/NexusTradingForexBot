# NSE Health / Safety / Governance — Architecture Map

Authoritative path from probe to pixel. Every verdict the operator sees is
generated by ONE of the two authorities below; the UI is a renderer, never a
decider (verified §3).

```
  PROBE (subsystem owner)      BACKEND COLLECTOR        AGGREGATION
  -------------------------    ----------------------   --------------------
  RiskEngine._kill_switch  ->  /api/debug/health (3) -> HealthEngine.overall()
  engine._last_fv          ->  /api/debug/health (3) ->   (legacy PASS/WARN/FAIL)
  engine._bundle/_last_probs-> /api/debug/health (3) ->   (state taxonomy word)
  engine.adapter._last_tick ->  /api/debug/health (3)
  AuditRepository          ->  /api/debug/health (3)
  sqlite/pg probes         ->  HealthEngine.check_* (2)
  MT5ConnectionState       ->  /api/mt5/status (5)
  NewsEngine.context       ->  /api/news/health (6)
  ForensicHealthEngine     ->  /api/forensics/health (7)
  engine.<worker>          ->  /api/v1/system/workers (4)
  engine._running          ->  /api/v1/system/runtime (4)

  AGGREGATION                API CONTRACT                 FRONTEND            UI
  -------------------------  ---------------------------  ------------------  ---------
  HealthEngine.overall()  -> /api/v1/system/health    -> useSystemHealth  -> MatrixCell
      (verdict + checks[])    {verdict, checks[],        (cells)             (cell tone)
                              critical_failures[]}
  HealthEngine.overall()  -> /api/v1/system/readiness  -> useReadiness      -> Layers tab
      (recomputed policy)     {ready, verdict,
                              required_layers[],
                              optional_layers[]}
  HealthEngine.overall()  -> /health (docker probe)    -> useProbe         -> badge
                             (503 when NOT READY)
  /api/debug/health (3)   -> DebugHealth               -> cellFromSubsystem-> matrix
                             {overall_status,
                             subsystems[], checked_at}
  /api/mt5/status (5)     -> Mt5Health                 -> cell (derived)   -> matrix
  /api/news/health (6)    -> NewsHealth                -> cell (derived)   -> matrix
  /api/forensics/health   -> ForensicHealth            -> cell (derived)   -> matrix
  /api/v1/system/workers  -> SystemWorkersV1           -> cellFromWorker   -> matrix
                             (NOT_ATTACHED reported)
  /api/v1/system/runtime  -> SystemRuntimeV1           -> engine chip      -> hero
                             (engine_running: _running)
```

## 1. Probe layer (backend, one owner per fact)

| Fact                     | Owner                                            | Probe fn                        |
| ------------------------ | ------------------------------------------------ | ------------------------------- |
| kill switch / risk clamps| `RiskEngine` (`risk/risk_engine.py`)             | debug-health route              |
| feature vector present   | `LiveEngine._last_fv`                            | debug-health route              |
| model bundle + inference | `LiveEngine._bundle`, `._last_probs`             | debug-health route              |
| broker IPC + tick        | `MT5Adapter._conn_state`, `LiveEngine._last_tick`| debug-health route              |
| audit DB write path      | `AuditRepository._worker_thread`/`._queue`       | debug-health route              |
| broker connection truth  | `MT5ConnectionState` (`adapters/mt5/diagnostics`)| `/api/mt5/status`               |
| news data freshness      | `NewsEngine.context` (`news/context.py`)         | `/api/news/health`              |
| forensic check matrix    | `ForensicHealthEngine` (`forensics/engine.py`)   | `/api/forensics/health`         |
| worker attachment        | `LiveEngine.<worker>` attrs                      | `/api/v1/system/workers`        |
| engine running           | `LiveEngine._running`                            | `/api/v1/system/runtime`        |
| env / config / data      | `release/health.py` `HealthEngine.check_*`       | `HealthEngine.overall()`        |

## 2. `HealthEngine` (release/health.py) — the DOCTOR authority

Static/offline checks. `run_all()` runs 24 checks, each failure-isolated by a
top-level `try/except` in `run_all()` (a raised check becomes `FAIL`/`ERROR`,
never crashes the sweep). `overall()` policy:

```
critical FAIL (CRITICAL_CATEGORIES: SYSTEM/RUNTIME/CONFIGURATION/DATABASE/
               MODEL/MODEL_CONTRACT/FEATURE_SCHEMA)  -> "NOT READY"
any other FAIL                                     -> "DEGRADED"
no FAIL                                            -> "READY"
```

`HealthEntry` carries BOTH vocabularies: legacy `verdict` (PASS/WARNING/FAIL)
and canonical `state` (state_taxonomy: AVAILABLE/DEGRADED/NOT_INITIALIZED/…).
`optional=True` means "never blocks READY by design".

## 3. `/api/debug/health` (web/debug_research_routes.py) — the RUNTIME authority

FIVE live widgets: Feature Engine, PyTorch Model, Risk Engine, MT5 Win32 IPC
Adapter, Audit Database. Each is wrapped in its own `try/except` (failure
isolation). Vocabulary: HEALTHY / DEGRADED / UNHEALTHY / DISCONNECTED.
`overall_status` = worst of the five. **This is the only place the live
subsystem verdicts (feature/model/risk/MT5/DB-runtime) exist.**

## 4. `/api/v1/system/*` (web/api_v1/system.py) — the READINESS authority

`_health_block()` runs `HealthEngine().overall()` (cached 3s on app.state).
`/readiness` recomputes its OWN `ready` bool from the check list:
`ready = verdict != "NOT READY" and no FAIL in required_layers`
(required = SYSTEM/RUNTIME/CONFIGURATION/DATABASE/MODEL/FEATURE_SCHEMA —
note: MODEL_CONTRACT absent from this list, present in CRITICAL_CATEGORIES).

## 5. `/api/mt5/status` — broker truth

Reads `adapter.connection_state()` (a real state machine, not config),
account snapshot, symbol spec, positions, orders, history. Never synthetic:
every failing read carries `error_state`.

## 6. `/api/news/health` — news truth

`NewsEngine.health()` returns `available` (subsystem liveness — True while the
module is attached), `state` (NewsState: NORMAL/ELEVATED/…/STALE — the
*derived-context* state), and `stale` (data freshness of that context). All
three are independent axes and all three are surfaced to the UI.

## 7. `/api/forensics/health` — forensic matrix

`ForensicHealthEngine.dashboard()` runs the check matrix on demand and
persists the snapshot to `artifacts/forensics/`.

## Frontend (React `/alt`)

`features/health/`: `api.ts` (typed transport) → `useCases.ts` (12 React
Query reads, independent keys, `retry: 0`, per-query `refetchInterval` 10s /
15s / 30s / 60s) → `model.ts` (pure DTO→cell mappers + `cellTone`/`matrixSummary`)
→ `ui/HealthPage.tsx` (matrix / layers / workers / identity tabs).

Cell independence is REAL: each cell carries its own `fetchedAtMs`
(`dataUpdatedAt` from its OWN query), its own error (failed cell →
`FailedCell` with its own retry), and its own age (`cellTone` vs the 10s poll
budget). Out-of-order protection is React Query's own: `dataUpdatedAt` only
advances; a late poll N response cannot overwrite poll N+1's newer data
(react-query keeps the latest observer data).

## Verdict ownership verdict (Phase 1)

| Verdict word       | Generated by           | Frontend action                     |
| ------------------ | ---------------------- | ----------------------------------- |
| PASS/WARNING/FAIL  | `HealthEngine` (backend)| mapped verbatim by `healthLevel`   |
| HEALTHY/DEGRADED/UNHEALTHY/DISCONNECTED | debug-health route (backend) | mapped verbatim |
| READY/DEGRADED/NOT READY | `HealthEngine.overall()` (backend) | hero badge, `probe.status` fallback |
| READY (readiness chip) | `/readiness.ready` (backend bool) | chip passthrough                |
| STOPPED/RUNNING (engine) | `engine._running` (backend) | chip passthrough                 |
| MT5 CONNECTED      | `/api/mt5/status` `available` (backend) | cell passthrough             |
| News ACTIVE/IDLE   | derived by the UI from `available`+`enabled` (**presentation-only**, no gate) | cell |
| NOT_ATTACHED       | `/api/v1/system/workers` (backend)     | cell passthrough             |
| good/warn/bad/neutral | `matrixSummary` (UI, **count-only** over backend verdicts) | counters |
| UNKNOWN            | `healthLevel` fallback (UI, presentation-only) | cell tone neutral            |

The UI maps and counts; it never *invents* a healthy verdict. The one UI-side
derivation is the overall page badge `DEGRADED-FAIL/WARNING/HEALTHY/UNKNOWN`,
used only as a *display fallback* when the backend verdict is absent
(`system.data?.verdict ?? probe.data?.status ?? overall`) — never to gate.
