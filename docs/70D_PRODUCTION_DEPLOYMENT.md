## 1. Deployment model

```
NEW INSTALLATION          EXISTING INSTALLATION
   |                              |
   v                              v
release bundle (portable)   nexus update check -> nexus update
   |                              |
   v                              v
first-start bootstrap       verify + backup + migrate
(DB bootstrap + migration   (SHA-256/manifest, atomic user-data
gate, model materialize)    backup, canonical migration engine)
   |                              |
   v                              v
health gate READY          install + health gate + COMPLETED
```

Central invariant: **NEW VERSION MUST SAFELY INHERIT THE USER'S OLD STATE.**
No database deletion, no model deletion, no research/accounting loss.

## 2. Package structure (portable, verified on release/v9.1.0)

```
NexusScalpEngine/
  NexusScalpEngine.exe        packaged launcher (onedir)
  NexusScalpEngine-CLI.exe    CLI shim
  build-info.json             build identity (version, commit, web hashes)
  release-manifest.json       release contract (embedded, brief §37)
  _internal/                  PyInstaller runtime + bundled Web/
  Web/                        index.html, app.js, api_client.js, styles.css
  configs/                    base.yaml
  artifacts/                  databases (user data — PRESERVED across update)
  data/  logs/                user data — PRESERVED across update (BUG-091)
```

User data separation (`release/paths.py`): installed layout keeps
databases/config/logs/models under `%LOCALAPPDATA%\NexusScalpEngine`;
the portable bundle keeps them in-tree and `ApplicationInstaller` preserves
`artifacts/ data/ logs/` across every update swap.

## 3. Release manifest (brief §37) — schema coverage (TASK-9)

Every release carries `release-manifest.json` generated by
`scripts/build/build_release.ps1` (via `update_helpers.py manifest`):

```json
{
  "product": "NexusScalpEngine",
  "version": "9.2.0",
  "git_commit": "...",
  "feature_schema": "scalp_v1",
  "feature_schema_dimension": 50,
  "supported_model_schemas": ["scalp_liquidity_v1", "scalp_v1", "scalp_v2", "scalp_v3", "scalp_v4"],
  "web_bundle_version": "<stamp-or-live-hash>",
  "db_schema_version": 7,
  "required_migrations": ["AUDIT-0002-...", "...", "AUDIT-0007-release-metadata", "NEWS-0002-...", "CANDLE-0002-..."],
  "model_compatibility": "scalp_liquidity_v1 (60D) / scalp_v1 (50D) / ...",
  "artifacts": [{"name": "...", "sha256": "..."}]
}
```

feature_schema / supported_model_schemas / db_schema_version /
required_migrations are DERIVED from the canonical schema registry + the
migration registry — never hardcoded (a 70D release cannot silently drift
the contract).

## 4. Runtime version identity (brief §15/§52)

`/api/status` → `versioning` block and `nexus version --json` expose:

- application_version, commit, channel, build_timestamp
- web_bundle_version (build-info stamp OR live content-hash of the ACTUAL
  served assets — a stale bundled app.js is caught)
- feature_schema (registry-derived id + dimension)
- database_schema (per-domain current/expected from the migration engine)
- version_status: CONSISTENT | VERSION_INCONSISTENCY (with `problems[]`)

`nexus model-artifacts` classifies every model artifact (ACTIVE / LEGACY /
RETAINED / ARCHIVABLE) with runtime compatibility and retention guidance.

## 5. Model deployment rules (brief §9/§11/§36/§38)

- Every model artifact keeps model_id, version, schema_id, dimension,
  schema_hash, artifact_hash, scaler_hash, algorithm versions
  (`nexus_scalp/release/model_artifacts.py`).
- 60D (scalp_v2 / scalp_liquidity_v1) and 70D (scalp_v4) are
  candidate-only; the ACTIVE live contract stays scalp_v1 until a separate
  governance decision changes it (INV-015/016).
- A 70D-capable model loads ONLY when: base scalp_v1 registered, dimension
  matches the registry, scaler present + hash-valid, and the liquidity
  producer is available (scalp_v4 / scalp_liquidity_v1). Otherwise
  MODEL_NOT_RUNTIME_COMPATIBLE with the exact reason — NO silent fallback
  (brief §14).
- Old 60D/50D models are never deleted by a release; classification
  determines retention only.

## 6. Deployment verification checklist (brief §21)

After every deploy/update, verify (read-only, no order placement):

1. application starts (`nexus health` → READY/DEGRADED)
2. database opens + migration state current (`nexus db status`,
   `/api/db/status`)
3. model registry loads (`nexus model-doctor --model <champ>`)
4. 70D schema registry loads (`nexus model-artifacts`)
5. UI serves (dashboard opens; versioning block visible)
6. API responds (`/api/status` JSON)
7. feature calculation works (state provenance MODEL_INFERENCE /
   ENGINE_STATE — never fabricated)
8. news + liquidity state available (truthful sections, UNAVAILABLE when
   not)

## 7. Operations / troubleshooting

| Symptom | Action |
| :--- | :--- |
| `VERSION_INCONSISTENCY` web bundle problem | rebuild the release (stamp + Web bundle together); the versioning block names the failing asset |
| `MODEL_NOT_RUNTIME_COMPATIBLE` | run `nexus model-artifacts`; the reason names schema/dimension/scaler/liquidity |
| `DB_DOWNGRADE_BLOCKED` | install a NEWER application; never delete the DB |
| `MIGRATION_FAILED` | backup path recorded; `nexus db status` + `nexus db repair`; never delete the DB |
| `UPDATE_BLOCKED_WHILE_LIVE` | run the documented `--force` maintenance quiesce first (INV-014) |
| update crashes mid-mutate | `nexus update status` → ROLLBACK_REQUIRED; `nexus update rollback` |
