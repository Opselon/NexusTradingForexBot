## The defect

Both tests are benchmarks. Wall clock is the wrong clock for a budget on a
shared CI runner: the suite runs on 2-core runners alongside co-tenant jobs, a
stalled runner slows the wall clock with zero change in the code under test,
and the budget trips. `time.perf_counter()` belongs to the *instrumentation*
concern, `time.process_time()` (CPU time) belongs to the *measurement* concern.
Same class as ML-QA-007/008/009/011/012/014; a red on only one OS of the matrix
is the tell, not a platform bug.

A second, independent defect in the research module: `big < small * 8 + 1.0`.
The `+ 1.0` additive pad on the small leg is a waiver (the ML-QA-014 compound
`assert A or B` class). At `n=1000` the whole measured leg costs ~10 ms, so a
one-second pad swamps the ratio term exactly where the O(n^2) regression it
guards for would show up first — the test carried no linearity guarantee in the
small-N region.

## Remediation (test-only, zero production files changed)

Both measured bodies run inside the shared `budget_cpu_ms` stopwatch from
`tests/e2e/chain_clock.py`, reading `sw.consumed_ms`. Both `import time`
statements are gone (the probes were their only consumers).

Budgets moved **with the clock**, calibrated against measured cost on this
2-core CPU-only host rather than ported from the wall-clock figures:

| Benchmark | Measured (CPU) | New budget | Margin | Old (wall) |
| --- | --- | --- | --- | --- |
| uniqueness 50k rows | 0.87 ms | 500 ms | ~570x | 2000 ms |
| sized path 4000/1000 ratio | 4.20x (per-sample 0.0108 ms, constant n=1000..8000) | 6.0 | over the true 4.20x | `* 8 + 1.0` |

Per-sample cost measured constant, so the ratio is a real structural invariant
(4x data costs ~4x CPU time by construction) and the battery adds a
per-unit-cost leg asserting it directly — a ratio can absorb noise in the small
leg, a per-unit cost cannot. The `+ 1.0` waiver is gone; the ratio is
unconditional.

## Battery-authoring defects caught pre-commit

1. **A rule quoting a string the module never carries** — `assert "u_i = (1 / L_i) * sum" in src`
   failed on the correct source (the module documents coverage by name, not by the
   formula string). Fixed to assert the coverage-list markers + durable-proof imports.
2. **A raw-substring rule matching its own explanation** — `assert "+ 1.0" not in body` matched
   the docstring that explains the removed waiver (`raw_substring_rule_sees_prose`, ML-QA-014
   class). Fixed by scoping to `_code_lines(body)`. Companion nuance: `_no_call` is token-typed
   (`NAME . NAME (` chains), the right tool for clock reads but tautological for an operator
   string like `"+ 1.0"` — that case needs a plain substring over executable lines.
3. **Module-level constant import at collection time** — `exec`-ing the analysed modules at
   battery import time would fail collection on any interpreter lacking torch/polars. Made lazy
   (`_budget_constant()`, resolves on first behavioural use, cached) so the textual rules
   collect anywhere.
