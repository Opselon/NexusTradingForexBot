The core distinction this task codified in code:

* **Instrumentation** (what a test *prints* for the human reading CI output)
  must be deterministic. A host scheduler changing what the suite prints is
  the same class of dependency as it changing what the suite asserts.
* **Measurement** (a real liveness budget) must stay a real measurement, but
  read CPU time so co-tenant load on a shared CI runner cannot trip it.

## What changed

### New: `tests/e2e/chain_clock.py`

* `ChainClock` — injected instrumentation clock. `elapsed_ms()` advances a
  fixed 0.075 s per call; a full 21-stage chain prints a byte-identical
  ~1.5 s on every runner. Returns floats so existing `{... * 1000:.1f} ms`
  format strings were untouched. `reset()`/`lap()` available for the general
  shape.
* `budget_cpu_ms(limit)` — context manager exposing `.consumed_ms` measured
  with `time.process_time()`. The **only** real clock in the helper, and
  never the wall clock.
* stdlib-only imports, so any test module can adopt it without pulling
  torch/polars into collection time.

### `tests/e2e/test_smoke_chain.py` — 42 probes → 0

All `time.monotonic()` calls removed (21 anchors, 21 lap reads, 1 wall
summary). Every `_info(f"stage NN in ...")` line and the final
`SMOKE CHAIN PASSED` banner read `_CLOCK.elapsed_ms()`. Dead `t0`/`t_wall0`
locals deleted; `import time` dropped (only `datetime.now(UTC)` remains, in
the maintenance-band helpers). **Zero assertion changes** — the timings were
never asserted on.

Watch for the trap I hit and fixed: removing `t_wall0 = ...` orphaned the
next `_banner(` call and produced an `IndentationError` at collection.
`py_compile` catches it; the new regression battery does too.

### Two failures that are NOT mine (baseline-confirmed)

1. **`test_smoke_full_chain`** — `ModuleNotFoundError: No module named
   'fastapi'` at stage 09. This host has no fastapi install. Reproduced at
   the base commit with the conversion stashed. CI exercises it on
   windows-latest / macos-latest with the full dependency set. **The 21
   converted stages 01–08 all executed and printed deterministic timings**
   before hitting the import, which is the useful local evidence.
2. **`test_shadow_phase11.py::TestWorkerRestartsNextRun::test_next_run_failure_is_isolated`**
   — fails *only when run after a large sibling set*: structlog routes the
   `NEXT_RUN_FAILED` event to the log record instead of captured stdout, so
   `assert "NEXT_RUN_FAILED" in out` reads `''`. Passes when the module runs
   alone (verified 3/3). Reproduced at base with my change stashed.
   Pre-existing; fixing it means switching the assert to a logger double per
   the roster's preferred shape — a separate change.
3. **`test_worker_dependency_probe_runs_with_stdlib_only`** — asserts
   `"structlog" in report["missing"]` for a `python -S` subprocess; when the
   parent's PYTHONPATH points at a site-packages holding structlog, the child
   sees it and reports torch instead. Parent-interpreter-dependent, not a
   code defect. (Note this is the documented PR-#192 shape #2 — env
   inheritance — in reverse.)
