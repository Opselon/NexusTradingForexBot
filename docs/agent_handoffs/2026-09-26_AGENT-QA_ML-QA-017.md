# ML-QA-017 — Training-Env Worker Suite Process-Identity Determinism

**Agent**: AGENT-QA · **Stream**: L (CI/CD & Verification) · **Date**: 2026-09-26
**Status**: DONE (PR pending) · **Task type**: test-only (zero production files changed)

## Summary

`tests/unit/test_training_env_worker.py` (push-gate module,
`tests/critical_suite.txt:481`) was the last open `os.getpid()` row of the
ML-QA-003 determinism census recount. Its subprocess test stamped the worker's
pid onto the progress line and asserted it differed from the parent's own
(an `import os` executed inside the test body). Two `os.getpid()` sources are
now gone; the transport contract the module pins no longer depends on which
pids the OS assigns.

## The defect

A process identity is not a contract value. The parent read its OWN pid and
asserted the worker's differed from it. No production path compares the two, so
the magnitude carried no information — the suite passed identically on any two
pids the OS assigned.

The assert was also a **proxy with a blind spot**. It stood in for "the
transport delivers ONE worker process identity across the whole run" (the pipe
protocol stamps the identity at the progress stage AND the result stage), but
comparing against the PARENT's pid cannot prove that: a regression that routed
the result line through a different process than the progress line still yields
a worker pid different from the parent's, so the old assert passed while the
continuity invariant it pretended to prove broke.

The battery's `test_a_fork_between_the_stages_breaks_continuity` leg
demonstrates the blind spot **empirically**: its split-identity fixture stamps
`os.getpid()` on the progress line and `os.getppid()` on the result line. The
result line's identity IS the test process's own pid, yet the old assert
(`worker pid != parent pid`) still passes on the progress line alone. Only the
cross-stamp comparison catches the discontinuity.

## The remediation

- The parent's pid read is consolidated into ONE injected supplier (`_pid`), so
  the semantic "the observed identity is not the parent's own" survives but
  asserts a STABLE IDENTITY rather than an OS-assigned number.
- The continuity invariant is now asserted between the transport's OWN two
  stamp sites (`metrics["pid"] == result["second_pid"]`), driven twice:
  - `test_real_subprocess_streams_progress_and_result` — the real-pid leg:
    continuity between the two stamp sites AND isolation from the parent's own;
  - `test_transport_reports_one_worker_identity_across_the_run` (new) — a
    FIXED identity (`_FIXED_ID`) makes the continuity reproducible to the digit,
    and its isolation leg (`_FIXED_ID != _pid()`) cross-checks the real-pid leg
    so neither passes alone.
- Both tests source their worker from ONE `_identity_fixture(root, fixed)`
  helper that stamps the SAME expression on both transport lines — two
  separate stamp expressions could drift, which is exactly the regression the
  old assert could not catch.

Production byte-identity is pinned by a battery rule
(`test_no_production_file_changed`, an executed `git diff --name-only
origin/main..HEAD` over the repo root).

## Battery-authoring defects caught pre-commit

1. **The ML-QA-016 text-walker over-counts a string literal on a code row.**
   The fixture builder selects its stamp with
   `str(_FIXED_ID) if fixed else "os.getpid()"`. That string literal sits on an
   executable line, so the ML-QA-016 `str.find`-based `_call_spans` matched it
   and reported the module's live `os.getpid` reads as two instead of one —
   the "exactly one supplier" rule failed on the correct source. **Fix**:
   `_call_spans` is now TOKEN-based (a real `NAME . NAME` chain followed
   directly by `(`), so a string literal containing the call text does not
   count. This is the ML-QA-017-specific form of the raw-substring rule that
   matched its own docstring in ML-QA-014/015, one level subtler: the literal
   is *on a code row*, so only token typing distinguishes it from a call.
2. **A `del` on a module attribute leaks across modules.** The behavioural
   legs first set and deleted `dispatch.worker_script` directly; `del` removes
   the attribute the production module defines, so a later test in a different
   file that calls the real `worker_script()` raised `AttributeError`. Fixed
   with `monkeypatch.setattr` + `monkeypatch.undo()` in the `finally` block.
3. **`os.getppid()` in the negative-control fixture resolves to the test
   process's own pid**, not a "different" identity as first assumed. Turned
   from a surprise into the point of the leg: it is the *empirical proof* of
   the old assert's blind spot (the result line carries the parent's own pid
   and the old assert still passes).
