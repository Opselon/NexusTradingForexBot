## 1. What was wrong

`tests/unit/test_outcome_flush_race_bug140.py` (push-gate module,
`tests/critical_suite.txt` line 405) carried 7 live non-determinism sources
per the ML-QA-003 census — two distinct classes, and neither was needed by any
assertion:

**(a) Wall-clock liveness bound — 4 `time.monotonic()` probes.** Both poll
loops bounded *themselves* on the wall clock: `deadline =
time.monotonic() + N`, polled inside a `time.sleep()` loop. That measures how
long the OS gave the test, not the code under test. Under `xdist` saturation
on a 2-core CI runner a co-tenant scheduler stall inflates the wait with zero
change in the contract, and the bound trips while the contract holds — the
same shape ML-QA-009 fixed for the audit-flush bounded-wait. The real
invariant was already the loop's *exit condition* (`row is not None`,
`stalled_queue.unfinished_tasks == 1`): the loop EXITS instead of hanging. A
genuine hang is caught by the CI-level test timeout, never by a wall-clock
magnitude assert.

**(b) Read drift — 3 `datetime.now(UTC)` reads.** The decision timestamp
(`_record`) and the two outcome timestamps read the clock independently. No
assertion compares any of them to `now()` — the clock contributed nothing —
but independent reads made the suite's own causality window
scheduler-dependent. The causality guard is **strict**
(`outcome_timestamp < decision_timestamp` at `ledger.py:506`,
`ledger.py:323`, `intelligence.py:756`), so an EQUAL decision/outcome pair is
accepted on the write path and merged on the read path. Under independent
reads that equality was a coin flip across a clock tick, and a date-boundary
stall could stamp the outcome in a different day from the decision.

Because no production path compares the supplied timestamps against the real
clock (unlike the shadow70 freshness gate of ML-QA-011), the frozen instant is
a **fixed calendar value**, not a captured read — nothing can age it out.

## 2. Remediation (test-only)

- One module-level frozen instant `_FIXED_NOW = datetime(2026, 9, 25, 12, 0, 0,
  tzinfo=UTC)` reached through a single `_now()` supplier. All 3 former
  `datetime.now(UTC)` sites read it: `ts = _now()` in `_record` and
  `outcome_timestamp=_now()` in the two outcome tests.
- Both poll loops bounded on **CPU time**: `budget_cpu_ms(...)` (the shared
  `tests/e2e/chain_clock` helper ML-QA-004/007/008/009/010/011 standardised
  on) wraps the loop, an inner `time.process_time()` bound is the fail-fast
  exit, and `sw.consumed_ms < limit` is asserted. The `time.sleep()` sleeps
  are gone.

`time` stays imported — `time.process_time()` is the CPU clock the bounds
use; the removed shapes were `time.monotonic()` and `time.sleep()`.

**Extractor note (for the next battery author).** The ML-QA-011 helper this

into code on a later physical row keeps the comment row verbatim — which made

`ast.walk` node line spans instead. `ast` is safe to import in this tree (no
`ast.py`/`re.py` shadows the stdlib anywhere under the repo root, verified);
`re` is still avoided in textual batteries for the shadowing reason recorded
