## Summary

`tests/unit/test_causal_conv_invariants.py` carried 4 live
`time.perf_counter()` reads inside its two latency benchmark tests. Both tests
measure a forward-pass budget and a cost-vs-receptive-field-depth ratio on a
push-gate module, and both used the wall clock — which on a 2-core shared CI
runner measures the co-tenant scheduler load rather than the model. A stalled
runner slows the wall clock with zero change in the code under test, and the
budget trips. That is the same class ML-QA-007/008/009/011/012 fixed
(`perf_counter` for *instrumentation*, `process_time` for *measurement*), and
the one-OS-of-the-matrix red is its tell.

Remediation is test-only — zero production files changed, pinned by a battery
rule (`test_no_production_file_changed` asserts an empty `origin/main..HEAD`
diff).

## Why the margins are honest

Measured on this 2-core CPU-only host (torch 2.14.0+cpu), blocks ∈ {3,4,5,6},
20 reps each, `process_time`:

| schedule | worst/best | worst-case per pass | budget | ratio bound |
|---|---|---|---|---|
| geometric | 1.52x | 0.87 ms | 50 ms (~58x) | 15x |
| linear | 1.48x | 0.84 ms | 50 ms (~60x) | 15x |
| fibonacci | 1.47x | 0.85 ms | 50 ms (~59x) | 15x |

Cost grows ~linearly with block count — dilation skips taps, so a deeper stack
does O(blocks) extra work at fixed sequence length. The ratio bound of 15 is
therefore ~10x over the observed 1.5x while still orders of magnitude below what
a padding defect (growing the tensor instead of dilating) would cost. The 50 ms
CPU budget is ~60x the observed worst case.

## Two battery-authoring defects caught before commit

1. **A raw-substring rule matched prose.** `assert "process_time" not in src`
   failed because the class docstring *names* `time.process_time()` to explain
   the clock swap — the very mechanism the module documents its own fix with.
   Fixed to a call-shape check on executable lines (`_no_call(code,
   "time.process_time")`), so docstrings are permitted and a real direct read is
   not. Same class as the ML-QA-013 tautology trap.
2. **A marker-string rule asserted a comment, not the code.**
   `test_latency_measurement_is_stable` has no `# warm-up` comment (only
   `test_latency_bound_across_rf_depths` does), so searching for the literal
   "warm-up" word asserted a comment rather than the behavior. Fixed to assert
   the actual `for _ in range(5):` warm-up loop precedes the measured leg in
   both tests.

Both were caught by the negative-control run, which is exactly what the control
is for: a rule that passes on the pre-remediation text proves nothing.
