## What was wrong
`tests/unit/test_experiment_registry.py::test_benchmark_1000_records_top10_under_50ms`
(manifest line 357, push-gate, runs under `pytest -n auto`) used 4
`time.perf_counter()` probes and asserted the top-10 query finishes in
**< 50 ms of WALL CLOCK**. On a saturated 2-core runner the wall clock measures
the scheduler: a co-tenant load spike inflates either leg unevenly. This is the
exact class that forced `9279f1ea` to drop the parity-suite 1 ms SLA entirely
(remediated in ML-QA-007 / PR #411).

## What changed (test-only)
- Both legs (register-1000 loop + top-10 query) now measure
  `time.process_time()` — CPU time, preemption excluded by construction.
- Warmup: one register + finalize + `top_n` before the first timed probe, so
  sqlite connection/schema setup is not charged to leg 1.
- Kept hard: `n = 1000`, every-3rd finalize stride, `len(top) == 10`,
  best-element check, monotone ordering, `query_ms < 50.0` budget.
- One deliberate assert change: `register_ms > 0.0` -> `>= 0.0` (throughput was
  never gated; `> 0.0` on an idle CPU-time leg would be a new flake class).
- New battery `tests/unit/test_ml_qa_008_registry_cpu_budget.py` (6 tests,
  textual, slim venv) registered in `tests/critical_suite.txt` (239 paths).
