# NSE Swarm Run — 2026-09-12T15:55Z — Role 10 (Accounting/Forensics)

## Defect: BUG-262 — forensic close paths stamped DETECTION time as the trade's close time

### Root cause (file:line at e9debfc6, verified by live pre-fix probe)
Three accounting/forensics surfaces fabricated the close INSTANT instead of
reading it from the broker deal evidence they already had in hand:

1. `src/nexus_scalp/execution/lifecycle/reconciliation.py:158-160` —
   `reconcile_missed_closes` passed `close_time=now, entry_time=None` into
   `reconstruct_broker_outcome` even though the same `deals` list carried
   `closed_at` (adapter: `mt5_adapter.py:1081`, aware UTC from the deal epoch),
   and wrote the ledger autopsy row with `close_time=now.isoformat()` and
   `duration_sec=0.0` (reconciliation.py:216-226).
2. `src/nexus_scalp/execution/lifecycle/reconciliation.py:649` —
   `_autopsy_vanished_ticket` (S6 sweep): `close_time=now` where `now` is the
   manage-loop detection instant, while `matched_deal["closed_at"]` held the
   true close. Duration came from tracked `entry_time` to detection-now.
3. `src/nexus_scalp/experience/outcome_repair.py:245` —
   BUG-046 repair job stamped `close_time=datetime.now(UTC)` per repair: every
   historically-repaired outcome "closed" on the day the operator pushed the
   repair button, and `duration = now - decision_entry` fabricated days of
   holding time.

### Why it matters (accounting blast radius)
- `audit_ledger.close_time` is the field every accounting period bucket reads
  (`accounting/core.py:288` window SQL, `normalize.py:264` `closed_at`,
  `aggregation.py:108` `bounds.contains(t.closed_at)`). A restart at 00:05 UTC
  re-bucketed every unreconciled prior-day close into TODAY — daily PnL
  reports, circuit-breaker windows, and the drawdown timeline all shifted.
- `holding_duration` feeds `research/metrics.py:189`
  `avg_holding_duration_sec` and `intelligence/behavior_canonical.py:234`;
  reconcile zeroed it, repair inflated it to days.
- outcome_timestamp = detection time poisoned the close-vs-decision skew
  forensics this class of bugs (G3/BUG-259/260/261) exists to protect.

### Fix
- `outcome_recovery.py`: new `as_utc()` (normalizes datetime/ISO-string/epoch
  int deal-time shapes to aware UTC, None on garbage) + `broker_close_time()`
  (latest valid close stamp across the ticket's deal rows) +
  `CLOSE_EVIDENCE_TOLERANCE_SEC = 120.0` contamination guard — evidence must
  lie inside [entry/decision time, detection + 120s], so a server-local (G1,
  +3h) or otherwise domain-skewed stamp is REFUSED and the old fallback
  instant applies. Precision improves only when the domains agree; no new
  day-bucket is ever created from clock garbage.
- Reconcile path: close_dt from deals + ledger `open_time` → real
  `entry_duration`; `broker_outcome.close_time/entry_time` evidenced; ledger
  `timestamp_str`/`close_time`/`duration_sec` and experience
  `outcome_timestamp`/`holding_duration_seconds` all follow close_dt.
- Autopsy path: close_dt from position-ticket deal evidence (bounded by
  entry_time ≤ t ≤ now+tol), then now := close_dt so the existing
  reconstruct/ledger/experience chain all inherit the evidenced instant.
- Repair job: `close_time` from deal evidence (bounded [decision_ts,
  now+tol]); the persisted outcome's `outcome_timestamp` +
  `behavior.duration_sec` (when it was a zero) are corrected too — otherwise
  the UPDATE would re-persist the old corrupt stamp from the payload.
