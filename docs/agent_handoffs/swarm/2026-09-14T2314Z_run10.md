**Class:** P1 accounting-evidence loss. The criticality-aware enqueue's last line of
defense (queue saturated -> one JSON overflow file per financial row) had NO reader

## Fix (contract: bounded, idempotent, worker-thread-only)

`src/nexus_scalp/adapters/database/audit_repository.py`:
1. `_overflow_dir()` — ONE path-resolution site (writer + drainer + public count share
   it; a second hand-built path is the R2-orphan shape; pinned by source-count test).
2. `_drain_financial_overflow_due(conn)` — audit-worker IDLE pass only (queue produced
   no batch; never the tick path, INV-001): cadence <=1 pass/60s with the None
   first-due sentinel (BUG-273 class), batch <=500 oldest-first, replay of stored
   query+args on the worker's own connection. Safe by construction: every financial
   producer query is ON CONFLICT idempotent — a duplicate replay is a no-op.
3. Retire = rename-then-delete under `overflow_recovered/` (crash between replay and
   unlink can never lose the row twice — storage-hygiene discipline).
4. Poison (non-INSERT, unparseable, `__unserializable__` envelope) -> durably
   dead-lettered (bounded retention owns it), `financial_overflow_failed`, ERROR log,
   retired — never retried forever, never silent.
5. Writer cap `_FINANCIAL_OVERFLOW_MAX_FILES=5000`: past it the row goes to the
   dead-letter table INSTEAD of spawning another file (counted + CRITICAL log).
6. `overflow_pending_count()` public surface; debug_snapshot now emits
   `financial_overflow_recovered/_failed/_pending` beside the existing counters.
